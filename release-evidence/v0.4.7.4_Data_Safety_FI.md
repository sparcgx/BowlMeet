## 3. 失敗群組與觀察

### F1｜較新的本機資料被舊 IndexedDB 覆蓋（P1）

案例 FI-03/04/05/06/07/16/21：
- localStorage 為新 220 分、IndexedDB 為舊 100 分，啟動後記憶體、localStorage、IndexedDB 都變成 100。
- 只存在本機的新 session 被移除；新草稿 220 分回退 100 分。
- `persist()` 後立即 reload，在 120ms 延遲寫入前，222 分回退成 100 分。
- 關閉 IDB 連線後，localStorage 成功保有 220 分；重開仍被舊 IDB 的 100 分覆蓋。
- 原生 IDB 升版被另一分頁連線阻擋時，先輸入 240 分；放行啟動後回退 100 分。
- 合成的本機 `removed` tombstone 被舊狀態清空，本機 publicRecordState 回傳 `published`。**沒有發送雲端請求，不等於已證實正式 PUBLIC 重新公開或 Supabase 防復活失效。**

對應原始碼：initDataSafety 只要 saved 為 truthy 就 applyState，沒有判斷新舊；applyState 立即覆寫記憶體並鏡像到 localStorage。captureState.updatedAt 使用當下 Date.now()，不能把它當成可靠的既有提交版次。

### F2｜localStorage 失敗阻斷 IndexedDB 備援（P1）

案例 FI-08/09/10/11/12：
- sessions、meetups、roster 的 setItem 被注入 QuotaExceededError 後，呼叫直接拋錯，queue timer 為 null，IDB 沒有儲存新內容。
- 另以原生 localStorage 實際填滿測試 context，約寫入 5,210,112 個合成字元後捕捉原生 QuotaExceededError；後續 persist 也拋錯，IDB 仍是舊 100 分而不是 233 分。
- 此字元數不是跨裝置保證的儲存額度，也不是磁碟容量測量。
- FI-11 在 applyState/mirror 元件邊界注入中途寫入失敗，形成新分數／舊球聚欄位的混合鏡像，畫面仍宣稱主要資料已保存。這是 **元件層部分寫入測試**，不是已跑完所有 caller 的備份還原流程。

對應原始碼：persist/persistMeetups/persistRoster 將 setItem 放在 queueDbStatePersist 之前；mirrorStateToLocalStorage 一個 try 包住多個 key，出錯後只 console.warn，沒有回傳完整鏡像是否成功。

### F3｜原生交易回滾，但應用 Promise 未結束（P1）

案例 FI-13/14/15：在原生 put/delete request 成功後呼叫 transaction.abort()。
- 真實 abort event 有出現，三種交易皆確認資料回滾。
- idbPut、idbPutMany、idbDelete 的 Promise 在 750ms 觀察窗內仍 PENDING，未 reject。
- 原始碼等待 tx.oncomplete、監聽 tx.onerror，**漏接 tx.onabort**。
- 這不是 IndexedDB 原子性失效，也不是程式在 request success 就過早 resolve。

### F4｜不合法的 IDB 狀態被當成空資料套用（P1）

FI-17：在 IDB appState 放入 truthy 但不符合資料格式的物件，localStorage 原有合法 220 分。啟動後 sessions 在記憶體、localStorage、IndexedDB 都變成空陣列。
此案例注入的是 **應用資料格式損壞**，不是模擬實體資料庫檔案或磁碟損毀。

### F5｜兩條儲存路徑失敗，缺少未儲存警告（P1）

FI-20：localStorage 配額錯誤加上已關閉的 IDB 連線，記憶體仍有 220 分，畫面 safetyEngineSub 卻仍顯示「主要資料已由 IndexedDB 保存；localStorage 為相容鏡像。」。
測試斷言是儲存狀態呈現不應誤導；不是畫面能繼續顯示就代表已保存。

## 5. 後續修正順序（提案，尚未實作）

1. 啟動先驗證保存狀態與版本關係；無法確定時保留雙份原始資料、禁止自動覆寫，不以單一 Date.now 或「筆數較多」猜測新舊。保護 tombstone 與啟動中新增變更。
2. 拆開各儲存路徑的錯誤邊界，localStorage 拋錯不得跳過 IDB 寫入；成功提示必須等至少一條可靠路徑確認；兩者都失敗就明示「未儲存」，保留當前內容供匯出。
3. idbPut/PutMany/Delete 補上 onabort、單次結束保護與可重試錯誤處理，連線中止時更新實際儲存狀態。
4. 對部分鏡像寫入、草稿與刪除記錄定義完整提交／衝突策略，再以本 24 案例及新回歸測試驗證。可能涉及 local-only 儲存協調契約，需另外審核；本次沒有變更 Schema/DB_VERSION/Backup/Public payload。
5. 新版 native storage 回歸通過後，再驗證 iPhone Safari、已安裝 PWA、備份還原及斷網重開，不用舊的 UI smoke PASS 代替。
